const showCategoryDetailsPage = async (req, res, next) => {
    try {
        const id = Number(req.params.id);

        const category = await getCategoryById(id);

// Global error handler
app.use((err, req, res, next) => {
    // Log error details for debugging
    console.error('Error occurred:', err.message);
    console.error('Stack trace:', err.stack);

    // Determine status and template
    const status = err.status || 500;
    const template = status === 404 ? '404' : '500';

    // Prepare data for the template
    const context = {
        title: status === 404 ? 'Page Not Found' : 'Server Error',
        error: err.message,
        stack: err.stack
    };

    // Render the appropriate error template
    res.status(status).render(`errors/${template}`, context);
}); 
I used a global error handling middleware in Express. It logs the error details for debugging, determines the appropriate HTTP status code, and renders either a 404 or 500 error page depending on the error type.

AI
Good—this is a proper Express error-handling middleware pattern, and you’re using it in a structured way.

What you did well:

* Centralized error handling (good architecture choice)
* Logging both message + stack trace (useful for debugging)
* Mapping `err.status` to HTTP status codes (clean pattern)
* Separating UI concerns with dedicated `404` and `500` templates
* Keeping controller logic free from rendering error pages

One thing to watch: exposing `err.stack` to the rendered view can be useful in development, but in production it can leak internal implementation details. A common pattern is to only include stack traces when `NODE_ENV !== 'production'`.
